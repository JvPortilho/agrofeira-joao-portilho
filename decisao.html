Registro de decisão — AgroFeira

Atividade 06 — Desenvolvimento Web

Aluno: João Victor Portilho
Projeto: AgroFeira

1. Objetivo

Este registro reúne as decisões de desenvolvimento do AgroFeira, projeto voltado à apresentação de produtos de produtores da região de Paragominas. O objetivo é comparar três maneiras de construir a interface: CSS autoral, Bootstrap e Tailwind, avaliando qual delas faz mais sentido para a continuidade do site.

A análise considera a organização do código, a adaptação a diferentes telas, a acessibilidade, a interatividade e os resultados observados nos testes do catálogo e do formulário de pedido.

2. Comparação das alternativas

Características das três abordagens
Critério CSS autoral Bootstrap Tailwind
Organização As regras ficam nos arquivos CSS do projeto, com controle direto sobre seletores e variáveis. Classes e componentes padronizados reduzem o trabalho de criar estruturas comuns. Classes utilitárias são combinadas diretamente no HTML.
Responsividade Exige planejar as media queries e o comportamento de cada elemento. Oferece grade responsiva, pontos de quebra e componentes adaptáveis. Oferece variantes responsivas para aplicar estilos por largura de tela.
Personalização Maior liberdade para definir a identidade visual sem depender de componentes prontos. Pode ser personalizado com variáveis e CSS adicional, como no AgroFeira. Permite compor estilos com utilitários e configuração do tema.
Interatividade Interações como menus e janelas precisam ser implementadas separadamente. O JavaScript do framework oferece menu recolhível e modal. Os utilitários de estilo não fornecem, por si só, a lógica de um modal ou menu.

Na experiência com o AgroFeira, o CSS autoral foi importante para definir cores, tipografia e a aparência das páginas. Já o Bootstrap facilitou a criação do catálogo em cartões, do menu para telas pequenas e da janela de detalhes do açaí.

O Tailwind é uma alternativa viável para estilização por classes, mas não substitui sozinho o JavaScript necessário para essas interações. Essa comparação descreve as características das abordagens e os resultados observados no catálogo Bootstrap, sem representar uma medição equivalente de desempenho das três versões.

3. Resultados dos testes

3.1 Menu responsivo

Na largura de 360 px, o menu foi exibido de forma recolhida, com um botão para mostrar os cinco links de navegação.

Ao abrir e fechar o menu, a inspeção do navegador mostrou a mudança do atributo aria-expanded de false para true e vice-versa. Os cartões continuaram organizados em uma coluna.

3.2 Janela de detalhes do açaí

O botão "Ver detalhes" abriu uma janela com a imagem, o produtor, o preço e a descrição do açaí.

Na visualização de 360 px, o conteúdo permaneceu legível. O fechamento pela tecla Esc funcionou e o foco voltou ao botão que havia aberto a janela, permitindo continuar a navegação pelo teclado.

3.3 Validação do formulário

O formulário de fechamento do pedido contém nome completo, e-mail e uma caixa de aceite das regras.

Com JavaScript ativado, a tentativa de enviar os campos vazios apresentou bordas vermelhas e mensagens específicas para cada campo.

O arquivo validacao.js foi carregado com resposta HTTP 200.

3.4 Funcionamento sem JavaScript

Com o JavaScript desativado, o formulário continuou visível, mas não apresentou as mensagens de validação.

Como o elemento form usa novalidate, o navegador permitiu o envio vazio, resultando em uma URL com ?nome=&email=.

Limitação encontrada: A validação atual depende do JavaScript. Uma melhoria seria preservar a validação nativa quando os scripts não estiverem disponíveis e acrescentar validação no servidor caso o projeto passe a receber pedidos reais.

4. Medição dos arquivos JavaScript

As medições foram observadas na aba Network do Chrome durante os testes das páginas publicadas.

Valores observados no navegador
Arquivo Transferido Tamanho do recurso
bootstrap.bundle.min.js 25,2 kB 80,5 kB
validacao.js aprox. 0,6 kB aprox. 0,6 kB

O Bootstrap traz funcionalidades prontas que economizam trabalho de implementação, mas acrescenta um arquivo JavaScript maior ao catálogo.

O script de validação do checkout é pequeno e tem uma responsabilidade específica. Os valores representam as medições observadas, não uma comparação completa de velocidade entre frameworks.

5. Acessibilidade e pontos de melhoria

O catálogo utiliza um link para pular ao conteúdo, textos alternativos nas imagens e um menu identificado por aria-label.

O botão do menu informa seu estado com aria-expanded. A janela de detalhes possui título associado e permite fechamento pelo teclado com retorno do foco.

No checkout, os campos possuem rótulos e as mensagens de erro são relacionadas por aria-describedby.

Os testes visuais confirmaram a exibição das mensagens. Porém, isso não substitui uma avaliação com leitor de tela nem uma validação automática completa do HTML.

Como próximos cuidados, é importante validar as páginas em um verificador HTML, testar a leitura das mensagens com tecnologia assistiva e corrigir a dependência de JavaScript no envio do formulário.

6. Decisão final

Para continuar o AgroFeira, a opção mais prática é combinar Bootstrap com o CSS autoral que já faz parte do projeto.

O Bootstrap ajuda a manter a organização dos cartões e oferece componentes responsivos e interativos, enquanto os estilos próprios preservam as cores e a identidade visual da feira.

Essa escolha também facilita a manutenção: em vez de desenvolver novamente o comportamento de um menu recolhível ou de uma janela de detalhes, é possível utilizar componentes conhecidos e concentrar o trabalho nas necessidades do site.

Ainda assim, usar componentes prontos não garante acessibilidade automaticamente. Cada interação precisa ser testada.

O principal ponto a melhorar é a validação do checkout. O teste sem JavaScript mostrou que os campos vazios podem ser enviados.

Para uma próxima versão, pretendo manter uma proteção nativa do navegador quando os scripts estiverem desligados e, se houver pedidos reais, validar os dados também no servidor.

Dessa forma, a praticidade do framework não fica acima da confiabilidade do formulário.
